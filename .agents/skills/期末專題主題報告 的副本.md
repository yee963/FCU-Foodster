#### **一、專題概述（Planning）**

**1.1 動機與背景** 逢甲大學周邊美食眾多，但學生在用餐高峰期常面臨三大痛點：首先是排隊耗時，買飯動輒需等待 20 分鐘以上；其次是外送門檻高，單人訂購需負擔高額運費或未達起送價；最後是收款混亂，傳統用 Line 揪團，團長在統計金額與代墊款項時極易出錯。本專題旨在建立一個校園專屬的揪團平台，解決上述真實存在的社交與生活問題。

**1.2 目標使用者** \* **逢甲大學學生：** 核心使用者，有訂餐需求但希望節省運費與等待時間者。

* **校園周邊店家：** 潛在受益者，透過團購增加訂單量。  
* **宿舍管理人員/領餐點：** 藉由明確取餐點減少校門口交通混亂。

**1.3 專題目標** \* **目標一：** 建立智能揪團機制，媒合鄰近使用者共同訂餐以平攤運費。

* **目標二：** 自動化帳務統計，解決團長人工計算與收款的繁瑣流程。  
* **目標三：** 整合地圖與取餐定位，提升學生用餐效率與精準領餐。

#### **二、需求分析（Requirements Analysis）**

**2.1 功能性需求（Functional Requirements）**

| 功能編號 | 功能名稱 | 功能描述 |
| :---- | :---- | :---- |
| **F-01** | **智能揪團系統** | 使用者可發起或加入團購，設定結單時間與校內取餐點（如翰英館、圖書館）。 |
| **F-02** | **自動拆帳與收款** | 系統自動根據點餐項目計算每人應付金額，並紀錄團員付款狀態。 |
| **F-03** | **美食地圖與評價** | 整合周邊店家菜單資訊，提供基於學生評論的推薦功能。 |

**2.2 非功能性需求（Non-functional Requirements）**

| 類別 | 需求描述 |
| :---- | :---- |
| **效能** | 系統應能在 2 秒內處理訂單數據更新，確保多人同時操作不卡頓。 |
| **安全性** | 使用者帳號與付款紀錄需進行基礎加密，防止資料外洩。 |
| **易用性** | 介面設計需符合行動裝置操作習慣，讓學生在 1 分鐘內完成入團動作。 |

**2.3 範圍限制（Out of Scope）**

* 本次不包含：與第三方支付 API 的實體金流串接（僅做紀錄模擬）。  
* 本次不包含：即時 GPS 真實定位（僅以文字/靜態地圖顯示預計位置）。
